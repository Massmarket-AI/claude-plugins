# Massmarket Claude Code plugins

The plugins every Massmarket teammate runs in Claude Code. They update themselves: once installed,
each new release reaches your computer on its own (Claude Code checks for updates when a session
starts, and the new version loads the next time you open it).

| Plugin | What it does |
| --- | --- |
| `mm-hooks` | Keeps the Massmarket worklog hook on this computer current. It only updates a hook the installer already set up; it never installs one, and never touches your token, your tracked folders or your settings. It also keeps the time tracker extension current in Google Chrome: when a session starts it writes the published release it carries into the folder Chrome loads the tracker from, and the tracker (0.11.5 and later) reloads itself within 5 minutes. It writes only into a folder Chrome lists as the tracker's unpacked install, only when that folder holds the tracker (its exact key) at a lower version, never into a git working copy, and never where a profile that loads it has Developer mode off; `manifest.json` goes last, and nothing in the folder is deleted. At most once a day it also tells Claude when a work Chrome profile (one signed in with an @massmarket.ai account) used in the last 7 days has no tracker installed, naming it by that address, and when Developer mode is off where the tracker is loaded. A profile with no @massmarket.ai account is never named or counted, and no address is written anywhere. It reads Chrome's settings on this computer only and sends nothing anywhere. It also keeps both Massmarket plugins current where Claude Code's own plugin auto-update is off: at most every 6 hours, in the background after a session starts, it reads each plugin's latest version from this repository and, for a plugin installed at user scope that is behind, runs `claude plugin marketplace update massmarket` and then `claude plugin update <plugin> --scope user`. Where Claude Code's auto-update is fully on it leaves the update to Claude Code and steps in only after the same new version has waited 2 hours. It never installs a plugin you do not have, never turns on one you turned off, never downgrades, never accepts a marketplace-declared install command, and never writes your settings; it records what it did in `~/.claude/mm-hooks/plugin-sync.json` and `plugin-update.log`. Set `MM_PLUGIN_SELF_UPDATE=0` to turn it off. |
| `mm-bridge` | It shows who needs you in a strip above the prompt in every thread and in a side pane (and says who holds a client's reply drafts once someone has picked them up), names and pins each client's thread, and never sends anything to a client. A client's thread is pinned while something of it is due within the next 24 business hours, and unpinned once it is clear. Each client has one chip: in its own thread when it has one (Do it here), otherwise in the thread you are working in; the strip in the other threads says where it is. When something new arrives for one of your clients, the bridge updates that client's thread for you, the same way Update thread does, except that it never picks up the reply drafts: it shows them, and a teammate can still take them. It waits until it has seen the same thing for 10 minutes, and until the reply drafts are ready or two hours have passed since it first saw the client's message. It never sends into a thread you used in the last 10 minutes, sends at most 3 such updates at a time and 12 an hour, and sends none on a computer whose time-tracking hook is older than 0.11.5. A client whose thread has been quiet for more than 7 business days gets its update in that same thread: no new thread is started for it. Right after Claude is asked to start a new thread for that client, its old thread is left alone while the new one starts. A client keeps its thread until you archive or delete that thread. If you use two Claude profiles on this computer, a client whose thread is in the other profile keeps it: in this profile its row offers Start thread, and nothing is started or sent for it by itself until you are back in that profile. A client with no linked thread first gets back the newest open thread that began with its own `[mm-link]` marker; a thread whose title only looks like the client never counts. Type `/mm auto off` to stop these updates. A client with no thread waits for you to press Start. A thread that gets long is compacted by Claude Code instead of being replaced. Starting a new thread always takes your own words: Start on a client's row and typing `/mm start <client>` put "Start <client>'s thread" in your prompt box, and Start missing threads (or `/mm start all`) puts "Start the missing client threads" there; press Enter to send it, or type those words yourself. Claude then starts each thread, and the app asks you to allow each one. A draft already in your prompt box is never written over: the button tells you what to send instead. No cards are put up, and nothing starts a thread by itself. Each request starts at most 8 threads, without picking up their reply drafts, and the new thread links to its client by the `[mm-link]` marker its first message opens with. The strip's button is Start missing threads; with none missing it reads All threads started. The pane has the same button when two or more clients need a thread. Type `/mm` to open the list. Open thread and Update thread take you to the thread by opening its link with your computer's own link opener. A client whose reply drafts a teammate holds is listed under "With a teammate" and is not pinned. A client whose only items were due before Wednesday, October 14, 2026 is listed under "Older", so nothing drops off the list without a trace; everything still open since then stays on the list until it is closed. A pin you take off by hand stays off until something new arrives for that client, or until what it is for goes overdue: then the thread is pinned again, once (take it off again after that and it stays off). After you send or discard a reply draft, the list updates within seconds. A press whose refresh meets a server error from the Onboarding Wizard, or no answer, asks once more before it says it couldn't refresh the list. A thread linked automatically stays linked once you send or close a reply through its pane or a route in that thread; anything else, type `/mm link <client>` in it. A thread the bridge linked by itself moves to the client's newest thread (one that opened for that client, or whose sessions worked on that client alone); a thread you linked yourself stays linked. Claude can relink a client when you ask, as long as the bridge (not you) made the old link. For the founder, a reply that waits for his OK is on his list whoever owns the client. For the founder and the PMs, the pane also lists "New people" above it: someone who wrote to us and whom no project matched, newest first, with what to check first and a Source link. Route to project (pick the project, then Route), Start project and Not client mail (for a HighLevel Directory lead: Mark handled and Not client mail) each make one call to the Onboarding Wizard; the person leaves the list once it answers, otherwise the row says what it answered. Nothing of theirs goes to Claude, and an Onboarding Wizard that does not send them yet shows no such section. Type `/mm rc on` to give each pinned thread Remote Control automatically, and take it off again when the thread is unpinned if the bridge turned it on; off unless you turn it on. Since 0.6.0 every thread you work on a client in is linked to that client: the client's first thread is its primary thread (pinned and named as above), and any other is a second thread, never pinned, renamed or sent anything, whose pane says which thread holds the reply package. A thread is linked when it loads the client's project skill, opens with the client's `[mm-link]` marker, or you link it; a skill load never takes a client from another thread. The side pane opens by itself in each such thread, and again on each surface you open the thread on, with a Tracking part at the top: the task the thread declared, the client's tasks and threads today, the time tracked to the client across all of them today and this week (the week is refreshed every 30 minutes), and leverage when the Onboarding Wizard shows it to you. Close the pane and it stays closed in that thread until the thread moves to another project. It never opens by itself in a run with `MM_UNATTENDED=1` or one whose first prompt begins `SINGLE-SESSION`, and opening it never picks up, claims or holds a reply package. The status line shows the client, the task and this thread's time today. A thread that has had two of your prompts without a client shows a strip with Track to <client> (when its title names one), Massmarket internal and Not client work; the first two leave a note for Claude to load the right skill. The time numbers appear once the Onboarding Wizard serves them; until then the pane says they are not available yet. |

## Install

Run the Massmarket installer from the time tracker extension. It adds this marketplace, installs
both plugins and turns on auto-update. By hand, in a terminal:

```
claude plugin marketplace add Massmarket-AI/claude-plugins
claude plugin install mm-hooks@massmarket
claude plugin install mm-bridge@massmarket
```

then set `"autoUpdate": true` on `extraKnownMarketplaces.massmarket` in `~/.claude/settings.json`.
Without it, mm-hooks 1.0.11 and later still bring both plugins up to date on their own, within about 6
hours of a release.

## Releasing

Anyone on the `pms` or `web-builders` team can release. A release runs on every teammate's computer
at their next session, so treat it like a deploy: test it on your own machine first.

`node scripts/release.mjs` copies the worklog hook from the onboarding-wizard `origin/main`, bumps the
version of each plugin that changed, validates, runs the bridge's tests, scans for secrets, commits
and pushes. `--dry-run` does everything but the commit and push. A push that does not bump a version
reaches nobody: the version number is the release.

With `MM_EXT_TOKEN` set to your own time tracker token, it also carries the published time tracker
release: it asks `GET /api/ext/version` what is published, downloads that zip, and keeps it only if its
manifest names exactly that version under the tracker's key (`scripts/carry-extension.mjs`). Without the
token the carried build stays as it is. Publish the extension first (`tools/publish.mjs` in the
massmarket-time-tracker repository), then release the plugin.

`main` keeps its full history: force pushes and deleting `main` are blocked (the org's "Keep history on
main" rule), so every release stays on record and any version can be restored with a normal commit.
